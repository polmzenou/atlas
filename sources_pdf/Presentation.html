Problème prioritaire : le serveur fait confiance au navigateur

GET /api/intervention/I200
Authorization: Bearer DEMO-U01-C01   ← Lina, C01
X-Tenant: C02                         ← choisi par elle

HTTP/1.1 200 OK
{"id":"I200","tenantId":"C02",
 "title":"Accès local réseau", …}     ← données de C02

http/isolement.http · back.mjs : db.byId(id) · config publique : tenant + chaîne SQL

  • A-01 Critique : tenant lu dans un en-tête ; vue SQL accessible depuis le navigateur.
  • A-03 Critique : affectation par GET, sans contrôle de tenant (T02 de C02 accepté), en 3 transactions séparées : un préchargeur réaffecte I100.
  • Une même cause : les écrans décident, l'API « enregistre ce que l'écran a validé ».

Architecture cible : une seule frontière de confiance

Monolithe et PostgreSQL conservés. La vue SQL et X-Tenant disparaissent. L'adaptateur v1 ne fait que traduire le format.

Un échange complet : deux planificateurs, même révision (U2)

1  Nora     PATCH /v2/interventions/I100
            If-Match: "rev-2"  {"priority":"HIGH"}
   → 200  ETag: "rev-3"

2  Collègue PUT …/I100/assignment
            If-Match: "rev-2"  {"technicianId":"T01"}
   → 412  {"code":"PRECONDITION_FAILED",
          "currentRevision":3}
     aucune mutation, aucun événement

3  Collègue GET …/I100 → priorité HIGH visible
4  Collègue PUT … If-Match: "rev-3"
   → 200 ASSIGNED · HIGH · rev-4
  • En base : UPDATE … WHERE revision = :lu et événement dans la même transaction.
  • If-Match obligatoire (428 sinon) : un client oublieux ne retombe pas dans « dernier écrit gagne ».
  • Écran : saisie conservée, relecture, renvoi sur confirmation (pas de répétition aveugle).

Un arbitrage : modifier sans perdre l'affectation (INC-04, R11)

OptionPourContre
PUT de remplacement completSimpleC'est le mécanisme d'INC-04 : un champ oublié devient null
JSON Merge Patch (RFC 7396)Standardnull veut dire « supprimer » ; aucun de nos champs n'est supprimable
PATCH générique avec statut et technicienUne seule routeMélange des rôles (la planificatrice ne démarre pas un travail)
Retenu : PATCH titre/priorité · PUT /assignment · POST /transitions« Conserver » et « changer » l'affectation sont structurellement distincts ; PUT idempotentTrois routes ; 422 FIELD_NOT_MODIFIABLE à documenter

Règle publiée : champ absent = conservé · null = refusé (422) · technicianId et status uniquement via leurs routes.

À retenir

  • Le serveur décide, à partir de l'identité validée : tenant, droits, règles, transitions.
  • Le contrat est le point de rencontre : codes d'erreur stables, ETag/If-Match, curseur, exemples vérifiés.
  • Migration par consommateur ; la sécurité n'est jamais réversible.
  • Hypothèses à lever par ATLAS : format de l'adaptateur Portail (H1), priorité numérique (H2), fuseau de I101 (H3).
