2. Architecture cible

Le monolithe et PostgreSQL sont conservés (P05, P09). La séparation en microservices n'apporterait rien aux défauts constatés. La cible place une seule frontière de confiance à l'entrée de l'API v2 : tout ce qui vient d'un client est une demande à vérifier ; tout ce qui décide (identité, droits, règles, transitions, révision, historique) s'exécute derrière cette frontière.

5. Accès aux données

Le schéma de stockage (P05) est conservé ; le modèle publié en diffère (createdBy, instants formatés, changes d'événement). Transformations : la ligne interventions devient l'objet Intervention, la ligne events enrichie d'une colonne changes (JSON) devient l'objet Event. Les contraintes ajoutées (migration de schéma) :

ALTER TABLE sites        ADD CONSTRAINT sites_tenant_uk UNIQUE (tenant_id, id);
ALTER TABLE technicians  ADD CONSTRAINT tech_tenant_uk  UNIQUE (tenant_id, id);
ALTER TABLE interventions
  ADD CONSTRAINT itv_site_fk FOREIGN KEY (tenant_id, site_id)       REFERENCES sites (tenant_id, id),
  ADD CONSTRAINT itv_tech_fk FOREIGN KEY (tenant_id, technician_id) REFERENCES technicians (tenant_id, id),
  ADD CONSTRAINT itv_status_ck   CHECK (status IN ('NEW','ASSIGNED','IN_PROGRESS','DONE','CANCELLED')),
  ADD CONSTRAINT itv_priority_ck CHECK (priority IN ('LOW','NORMAL','HIGH'));
ALTER TABLE events ADD CONSTRAINT events_rev_uk UNIQUE (intervention_id, revision);
CREATE INDEX itv_list_idx ON interventions (tenant_id, status, site_id, created_at DESC, id DESC);
CREATE INDEX itv_tenant_idx ON interventions (tenant_id, created_at DESC, id DESC);

Avec MATCH SIMPLE (défaut PostgreSQL), la FK technicien n'est pas vérifiée tant que technician_id est NULL, ce qui correspond à « aucun technicien ». L'activité du technicien reste une règle applicative vérifiée dans la transaction : une contrainte ne peut pas l'exprimer sans bloquer la désactivation d'un technicien encore affecté.

-- Liste, page suivante (tri -createdAt) : keyset, tenant imposé par le jeton
SELECT … FROM interventions
 WHERE tenant_id = :tenant AND (:status IS NULL OR status = :status) AND (:site IS NULL OR site_id = :site)
   AND (created_at, id) < (:cursor_created_at, :cursor_id)
 ORDER BY created_at DESC, id DESC
 LIMIT :limit + 1;                     -- la ligne en plus indique hasNext

-- Affectation : une transaction
BEGIN;
SELECT active FROM technicians WHERE tenant_id = :tenant AND id = :tech;      -- 422 si absent ou inactif
UPDATE interventions SET technician_id = :tech, status = 'ASSIGNED', revision = revision + 1, updated_at = now()
 WHERE id = :id AND tenant_id = :tenant AND revision = :if_match AND status IN ('NEW','ASSIGNED')
RETURNING revision;                                                          -- 0 ligne : relire pour choisir 404/412/409
INSERT INTO events (intervention_id, actor_id, kind, at, revision, changes) VALUES (…);
COMMIT;

6. Continuité v1 et migration des consommateurs

Principe (ADR-3) : un cœur unique /v2 ; l'adaptateur v1 reste le seul point de conversion ; migration consommateur par consommateur. Les correctifs de sécurité ne sont jamais annulés par un retour arrière (P09). Les dates sont des propositions à confirmer par ATLAS (N01).
